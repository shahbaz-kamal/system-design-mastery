# Pedagogy and answer-length policy

## Core goals
Learn system design concepts thoroughly, **not only pass interviews**. The chapter guide must stand on its own without constant reference to the book. The student learns slowly and may forget prerequisites; write for that reality without being patronizing.

## Each section's structure
1. **Learning outcomes** — what the reader will understand.
2. **Prerequisites / glossary** — 3–8 relevant terms, defined simply and accurately.
3. **Elaborative lesson** — the bulk of the depth lives here: problem, motivation, components, data flow, 1–2 real-life scenarios, common mistakes, trade-offs, failure modes, and a mini-recap.
4. **Worked example** — diagram/SQL/Node.js example when it clarifies the mechanism.
5. **Questions and answers** — integrated with this exact section, not all questions at the end.
6. **Answered follow-ups** — meaningful extensions, complete answers.

## Desired length and depth
- **Section explanation**: typically 600–1,200 words for complex material; 300–600 words for straightforward sections. Adjust to actual complexity and avoid filler.
- **Regular model answer**: typically 150–300 words, self-contained enough to stand alone but don't repeat the whole section.
- **Advanced design/capstone**: 300–550 words where needed.
- **Follow-up answers**: often 80–200 words, longer only for a hard concept.
- Definitions should be clear, not one-word glosses; examples should specify what sends data, where it goes, and what changes.
- A Q67-style clear explanation is a **style reference**, not a requirement to reproduce a whole tutorial per question.
- Use one consistent e-commerce / Node.js / PostgreSQL system across related examples, changing scenario when it clarifies a different trade-off.
- Avoid too many technologies in a single example. Introduce advanced dependencies only after explaining why they're needed.

## Study utility
- Add a 3–5 point 'Remember this' section to each lesson.
- Add a few recall questions or a mini scenario at the end of each section (with answers or answer key).
- At chapter end, include glossary, concept relationships, common mistakes, and a compact revision checklist.
- Mark source-based vs supplementary explanatory claims explicitly.
